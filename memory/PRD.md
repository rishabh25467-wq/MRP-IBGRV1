## Bug Fix: False-Negative "Missing SAP BOM" in Purchasing Plan (Feb 2026, Session 5 cont.)
- User reported ~30 OMS parts (FMF519, HTBS, NS-SPST2B, P26632, DM-0009, etc.) that genuinely have valid SAP BOMs were showing up in the Purchasing Plan's "Missing BOMs" warning as "No SAP BOM found".
- ROOT CAUSE: `server.py`'s `MongoClient` was instantiated without `tz_aware=True`. `bom_cache_service.py` writes `datetime.now(timezone.utc)` (timezone-aware) but PyMongo reads timestamps back as timezone-**naive** by default. `build_tree_from_cache()`'s `track()` helper compares a running `min_checked_at` against each node's `checked_at` while walking a BOM tree - the moment a tree mixed an already-cached node (naive, from Mongo) with a newly-discovered node in the same run (aware, freshly created), the comparison raised `TypeError: can't compare offset-naive and offset-aware datetimes`. `purchasing_plan.py`'s `explode()` broad try/except silently swallowed this into `None`, misreporting a perfectly valid, already-cached SAP BOM as "missing" - this happened on essentially any tree that touched even one previously-unseen product_id, which is extremely common.
- Fix: `mongo_client = MongoClient(os.environ['MONGO_URL'], tz_aware=True)` - datetimes read back from Mongo now stay timezone-aware, matching what's written, eliminating the mismatch at the source.
- Secondary fix: `bom_cache_service.py`'s `_fetch_live()` was single-shot with no retry (the flaky SAP tenant occasionally connect-timeouts under the concurrent load a plan run generates) - added a 3-attempt retry with backoff (same pattern as `sap_soap_client.py`'s existing sub-BOM retry), further reducing genuine transient false negatives.

- Fix: (1) both frontend polling loops now retry up to 5 consecutive failures before surfacing a real error instead of dying silently; (2) backend raised `DEEP_BACKFILL_MAX_WORKERS` 3→6 and switched to a time-boxed `ThreadPoolExecutor`+`as_completed` loop capped at `DEEP_BACKFILL_MAX_RUNTIME_SECONDS=360` (6 min) - already-resolved items persist immediately so a run that hits the cap just reports `stopped_early: true` and the user re-clicks the button to continue where it left off (no data lost, no re-checking of already-resolved items).

## Bug Fix: SAP BOM Fetch Cloudflare Overload (502/524) - Feb 2026, Session 13 - COMPLETE
- User reported: "preview is not pulling SAP bom and returning error cloudfare overload" on BOM Explorer, and correctly doubted it was a genuine SAP outage.

  1. `_query()`: split the single blended `timeout=15` into `timeout=(8, 15)` (connect=8s, read=15s) - the real failure mode is the TCP connect stalling, not a slow response body.
  2. `_safe_fetch_by_output_product()`: reduced retries from 3 attempts (escalating 1.5s/3.0s backoff) to 2 attempts (flat 1.5s backoff) - cuts one stuck item's worst case from ~49.5s to ~17.5s.

- **Residual known limitation (accepted, not fixed per user's explicit "not sure")**: the 40s deadline in `explode_bom()` still only checks between BFS batches, not mid-batch - under a worse-than-observed flakiness day, a batch of 8 concurrent lookups where multiple simultaneously hit the connect-timeout could still approach the deadline's edge. Testing agent's code review flagged this as "not a hard guarantee" but did not reproduce a failure in 8+ trials. If this recurs, the fix is: make the batch wait non-blocking (`concurrent.futures.wait(timeout=remaining)` against a persistent executor with `shutdown(wait=False)` at the end) so a slow batch can be abandoned exactly at the deadline instead of blocking to completion.

## Bug Fix #3: Genuine Parsing Bug Found - Wrong ECO Picked When Ties Broken By Name Not Date (Aug 2026)
User's screenshots (SAP's own BOM report via colleague "Kapil") showed FLAT-BK21 and CS14X48X1.2 as "used in BOM" while our app flagged both "No BOM". Investigated each individually via live SAP queries (raw `_query()` XML) rather than guessing.
- **FLAT-BK21 (BK-0021/BK-0025/BK-0130)**: our flag was CORRECT. Confirmed live: all 3 parents have exactly 2 whole-BOM revisions each, and ALL genuinely swapped FLAT-BK21 -> SH4.5HR between revision 1 and 2 (both revisions carry `ConsistencyStatus=3`, but the code's existing candidate-selection already correctly picks the higher-revision/current one). - **CS14X48X1.2 (P26675_1)**: this WAS a genuine parsing bug, now fixed. Root cause: SAP's response has TWO different representations of the same item-level change history - the nested `<ItemGroupItem><ProductionBillOfMaterialItemGroupChangeState>` records the code parses to build `groups` (used for the actual tree) carry NO date field at all, while a separate flat `<ProductionBillOfMaterialVariantItemChangeState>` list (same ItemGroupID+ItemID+EngineeringChangeOrderID key) DOES carry `EngineeringChangeOrderValidFromDate`. The code was picking between multiple change-states for the same line using only `_eco_matches_own_product` (naming-convention heuristic) + revision-number, with no date at all - so it picked ECO "P26675_1" (ValidFrom 2023-06-01, older) over "CUST14X4812" (ValidFrom 2023-08-01, genuinely current) purely because "P26675_1"'s name happened to match the parent product's own ID convention.
- **Fix** (`sap_soap_client.py`, `_build_bom_from_hit_blocks`): now cross-references the flat `VariantItemChangeState` list (keyed by group_id/item_group_item_id/eco_id) to get each change-state's real ValidFromDate, and uses `(valid_from, self_matched, revision)` as the comparison key - date wins first, the old heuristics only break ties when a date is missing/equal. Verified live: P26675 now correctly resolves to CS14X48X1.2 (`no_bom` flips True -> False); BK-0021/25/130 unaffected (still correctly SH4.5HR, that's a different, whole-revision-level mechanism untouched by this fix).
- Re-ran `refresh_stale_nodes` across all 4,679 cached Preview nodes to apply the corrected parsing catalog-wide. Net effect: 513 -> 514 no_bom (some other lines that were incorrectly benefiting from the old bug flipped the other way, i.e. correctly became flagged) - a small net change is expected and healthy for a correctness fix touching thousands of ECO'd lines, not a regression.
- **Status**: Committed. Needs a redeploy + "Run Full Sync Now" on Production to apply (same as the other two fixes in this session).
